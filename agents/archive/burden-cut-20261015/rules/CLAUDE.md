## 範圍：只做被要求的事

- 只做使用者明確要求的事情，不加沒被要求的功能、限制、驗證或「改進」。
- 現有功能還沒確定完整正確之前，不做新功能。
- 覺得該做但沒被要求的，用一句話提出來，不要直接動手。

不要過度工程：

- **選最簡單的正確實作**，不確定時先做能用的版本。
- **不為假想的未來需求寫程式碼。**
- **三行重複優於過早抽象** —— 出現第三次才抽。
- 不需要的就刪掉，不留 `_unused`、不寫 `// removed` 註解。
- Monolith first：沒有明確需要就不拆服務、不引 message queue。

## Session 結束

## 驗證：宣稱「修好了」的舉證責任

**「燈是綠的」不構成證據。** 宣稱修復或驗證通過時，必須同時附上：

1. **陰性對照** —— 證明這個驗證手段「會失敗」。注入一個已知的壞情境，它必須變紅。
   不會紅的綠燈是橡皮圖章。
2. **覆蓋率確認** —— 「N passed」要對照「幾條 skipped／根本沒執行」。
   「有在跑」不等於「有在驗」。

歸因宣稱（「根因是 X」）需要直接證據（死在哪一步的 log）。**時間相關性不是因果。**

- **覆蓋率不構成證據**：只呼叫函式而不驗行為的測試也能拿到高覆蓋率。
  宣稱「測試寫好了」要能說明**測試會因為程式碼被改壞而變紅**。

## 交付說明

每次交付要交代：

- 哪些檢查**跑了**、哪些**沒跑**
- 有沒有動到正式環境
- 影響範圍（公開介面／後端行為／資料庫結構／部署設定）
- 還剩什麼風險需要另外處理

**「沒跑的檢查」要主動講，不要等人問。**

## 除錯：使用者說「沒生效」時

使用者回報的現象跟我的驗證衝突時，預設是**我的測試有盲點**，不是使用者搞錯。

- **在使用者的狀態下重現**，不要只用乾淨環境。既有的 localStorage、cookie、快取、帳號資料、設定檔都要帶上。
- **一個原因要解釋全部症狀**。對方講三件事就要三件都解釋得通；假設只解釋得了其中一件，那就是錯的。
- **先查最奇怪的症狀，不是最好查的那個。** 最反直覺的線索資訊量最高。
- **講證據要同時講邊界**：「這個檢查證明 X，但證明不了 Y」。說不出邊界代表還沒想清楚。
- **卡住就先列三個可能原因再逐一排除**，不要鎖死在第一個看似合理的解釋。
- **爭議要給對方能自己驗的東西**（版本端點、log、可重現的指令），不要靠我口頭保證。

有證據不等於有結論 —— 能拿出證據最容易讓人停止調查、開始辯論。

## 測試時機

測試種類、時機與深度依任務風險和共用 cash-rule 工程政策決定。可用小型測試及早驗證假設；整合驗收與交付品質 gate 在方向明確後依政策完成。不要為追覆蓋率或變異分數延誤核心驗證。

## 提交前

- **格式化 + 靜態檢查 + 測試三關全過才提交**，任何一關紅就先修。
- 絕不提交編譯不過、格式錯誤、或測試沒過的程式碼。
- **迭代中只跑快的**（格式檢查、快速 gate）；**push／PR 前才跑全套**。
  不要每改一行就跑完整檢查 —— 那是浪費時間，不是嚴謹。

## 分層

- 路由層只做：驗參數、呼叫服務、對應錯誤。**業務邏輯不寫在路由層。**
- 資料庫存取收在資料層後面，不要散在 UI 或路由裡。
- UI 只負責渲染狀態與發出動作；取資料、持久化、轉換都放在別的地方。
- **設定值集中管理**，不要在應用邏輯裡到處讀環境變數。
- 長時間工作要能續跑、有日誌、盡量做成重跑無副作用。

## 重構

- 重構要朝「讓測試更好寫」的方向走。
- **行為保持的重構跟功能變更分開提交**，改動大的時候尤其。
- **不要為了看起來整齊而搬動無關的程式碼。**
- 不要重寫大型資料檔，除非任務本身就是資料遷移。

## 錯誤與日誌

- **所有錯誤都要被記錄，禁止靜默吞掉。** 預設 4xx 至少 warn，5xx 必 error（含堆疊與請求 ID）；repo 規則另有等級時從 repo。
- **錯誤走統一的錯誤出口**，不要各處自己 `console.log` / `println!` 散寫。
  目標：任何錯誤都在同一個地方看得到、格式一致、可告警。
- 日誌用結構化欄位，不要把資料塞進字串。
- **不記 PII**（姓名、email、電話）、不記 token 或密碼、不記完整 request/response body。
- 生產路徑不使用會直接中止程式的捷徑（Rust 的 `unwrap`/`expect`/`panic!`、
  JS 未接的 `throw`、Python 的 bare `assert`）。錯誤要往上傳，不是就地炸掉。
- 邊界（HTTP／CLI／服務進入點）補上下文再回報；領域層用具名的錯誤型別。

## 安全

- SQL 一律參數化，禁止字串拼接。
- 不 commit 憑證、`.env`、金鑰。
- Docker port 預設綁 `127.0.0.1`，不要暴露到 LAN。
- 不在日誌或錯誤訊息裡輸出敏感資料。

## 長時作業與自動化

- **長時間執行的功能必須可觀測**：禁止「按下去 → 黑箱 → 只有成功或失敗」。
  要能查到「做到哪、剩多少、卡在哪」。
- **單一請求撐不完（超過數十秒）的預設改背景工作**，不要硬塞進同步請求；服務架構另有規定時從 repo 規則。
- 所有自動化任務都要**可追蹤、可重試、可停用**。
- 單筆失敗要隔離，不能拖垮整批；要有「重複執行防護」，避免同一個工作被跑兩次。
- **不自動改寫使用者的原始資料**（改名、搬移、覆寫內容）。
  這類動作一律只給建議，要人工核准才執行。

## Git

- 主幹上 commit 與強制推送由 git_guard 擋下；被擋就開 `feature/` 分支或改一般 push。
- 小步提交：每個 commit 都是一個獨立、可編譯的變更。
- Commit message 用 Conventional Commits（`feat:` / `fix:` / `docs:` / `refactor:`）。

## 部署

- **改動先進測試環境驗過，再上正式。** 要直接動正式環境之前，先停下來確認。
- 跨 repo 的連動改動要講清楚 merge 順序，避免出現「前端送舊格式給新後端」的半上線狀態。
- 部署完要有辦法確認「線上跑的真的是這一版」（版本端點、build 標記），不要靠口頭保證。

## 設定與啟動

- **能寫預設值就寫在程式碼裡**，只有真正的 secret 和環境差異才用環境變數。
  空陣列、業務常數這種東西不該外部化。
- **「啟動就該 ready」的事綁在啟動流程**（初始化、warmup；migration 依 repo 的遷移策略），
  不要讓部署 SOP 多一步。
- 白話：寧願程式碼長一點，也不要部署手冊多一條。

## 事實（強制執行，cash 2026-09-07 定）

**禁止把推論當成事實講。** 每個事實主張都要附來源，而且來源必須經得起「它憑什麼可靠」這一問。

### 來源分級

| ✅ 可以當證據 | ❌ 不能當證據（這些是「主張」，引用前要先驗） |
| --- | --- |
| 實際會執行到的程式碼路徑（`檔案:行號`） | 程式碼註解 |
| 指令／測試／查詢的**輸出** | 文件、README、CLAUDE.md 自己 |
| 實測結果（真的跑起來看到的） | commit message、PR 描述 |
| 規範／官方文件**原文**（附章節或 URL） | loop 檔、handoff、看板卡 |
| 型別、schema、DB constraint 這類硬約束 | 其他 agent／模型的報告 |
| | 我自己先前講過的話 |

右欄那些描述的是**意圖**，不是行為——兩者會分岔，而且分岔時沒有任何徵兆。
要引用右欄，必須先去驗它講的是不是真的，然後引用「驗證的輸出」而不是它本身。

> 實例（2026-09-07）：`schema.prisma:859` 與 `auth.middleware.ts:131` 兩處註解都寫
> 「改密碼時遞增 mfaVersion」，實際上程式碼從來沒有這樣做。引用註解＝**帶著行號講錯話**，
> 比沒有來源更難被發現。同批還有一份 loop 檔記著「步驟 5b 完成」，而該功能從未接上。

### 講法

- **有驗過**：直接講死，附來源。
- **沒驗過**：寫「未查證」，不要當成事實講。不要用「應該」「推測」「可能」「我想」把推論包裝成答案。
  診斷或研究需要列假設時，標明「假設」並寫出哪個檢查能推翻它。
- **查不到**：說查不到。不要用合理推理填空——合理的推理錯起來最難發現。
- **來源與結論之間有跳躍**：把跳躍明說，或去補那段驗證。

### 邊界

講證據要同時講邊界：「這個檢查證明 X，但證明不了 Y」。說不出邊界代表還沒想清楚。

### 更正

- 講錯要立刻更正，說明錯在哪，不要淡化。
- 結果照實報：測試沒過就說沒過並附輸出；跳過的步驟要講。做完且驗過的就直說，不要加保留字。
