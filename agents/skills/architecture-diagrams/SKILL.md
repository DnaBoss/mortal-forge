# 架構與流程圖

使用者要的是從圖形空間與連線直接讀懂關係，不是把段落換成表格、文字列或箭頭清單。這是呈現偏好；不增加任務範圍、操作授權或外部發布權限。

## 選對圖

- 組件、部署位置、包含關係：系統架構圖。需要同時說明資料位置時，用「含資料流的系統架構圖」。
- 先後呼叫與回應：時序圖，參與者分欄，時間沿單一方向推進。
- 步驟、條件、重試、停止與回饋：流程圖，畫出分支及回到前一步的線。
- 數據比較才用圖表；純欄位對照可保留表格。使用者指定格式時優先遵守。
- 不必要求使用者說出圖的專有名詞；根據內容自行選擇。

## 圖上必須看得到的關係

1. 用有意義的位置、分組與巢狀框表達層級。框在裡面必須真的表示包含，不能只為好看而框在一起。
2. 用連接線及箭頭表達方向；把介面或傳遞內容標在線旁。需要說明回程時畫回程，不能只寫「沿原路回來」。
3. 程式控制、資料載入等不同類型的關係，使用不同線型及標籤；可搭配顏色與圖例，不能只靠顏色區分。
4. 程式、資料、硬體、儲存位置分開畫。不要把模型權重畫成會接 HTTP 的服務，也不要把程序內函式庫畫成另一個服務程序；其他領域遵循同樣的語意準確性。
5. 節點只放名稱及必要短句，說明與來源放圖外。文字框連成一列、每框塞一段原文，仍不符合這個偏好。
6. 關係太多時拆成總覽與局部圖；不要在單頁縮小到看不清楚。修改既有文件時，盤點所有相關頁，尤其使用者引用的那一頁，不能只改相鄰頁。

## 參考成品

首次使用本技能，開啟 [使用者認可的架構圖](references/approved-architecture.png) 看呈現方式；讀 [參考圖說明](references/approved-example.md) 了解哪些是可沿用的設計原則。

範例只代表使用者認可的視覺呈現，不是其他機器或未來版本的技術事實。不可不經查證照搬其服務、介面或硬體配置。

## 製作與驗收

- 聊天中的小型靜態圖，可用支援渲染的 Mermaid。PDF／簡報優先使用 SVG 或其他清晰的向量圖；需要互動才用互動視覺化。沿用交付格式的技能，不強迫換格式。
- 查證重要關係；對未知或示意配置明確標示，不為畫出完整圖而發明元件或接口。
- 實際查看最後交付的圖或 PDF 頁面，確認文字、箭頭、圖例、來源與頁尾沒有相撞、截斷；不能只以文字抽取或檔案生成成功作為驗收。
- 驗收問題：不讀長段說明，能否從圖上指出「誰包含誰、誰呼叫誰、傳什麼、資料在哪裡、下一步去哪裡」？只檢查本圖適用的關係。若仍必須逐段讀完文字才能理解，重畫。
- 交付說明指出改到哪些圖／頁與驗證範圍；不要宣稱新 session 或其他 AI 已實際測試，除非真的執行過。
