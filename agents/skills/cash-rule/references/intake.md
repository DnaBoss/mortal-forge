# 需求釐清與拆票（整合自 Matt Pocock 的 grilling、to-spec、to-tickets）

用途：新工作的需求不清楚或太大時，開工前先問清楚、拆小，再進 cash-rule 的計畫。需求已清楚、範圍很小就跳過，不為流程而流程。本檔不增加授權；結果寫進 LOOP 的「目標、整體驗收、計畫表」，不另開規格文件。

## 一、釐清（只問使用者獨有的決定）

1. 先自己查：程式、文件、網路能查到的事實一律自己查，不拿來問使用者（沿用「未知先研究」）。
2. 列出決定樹：每個決定下面會再牽出哪些決定。只有前提已確定的問題才能現在問。
3. 一輪問完所有能問的問題：每題編號、附你建議的答案，寫成「回答是就接受建議」。使用者答完再算下一輪。
4. 可逆的取捨自己選，不問；只問花錢、刪除、兩條路工作量差很多、或只有使用者知道的偏好。
5. 沒有問題可再問、也沒有悄悄做的假設時才結束。使用者還沒確認共識前不動手。

## 二、定規格（寫成 LOOP 的目標與整體驗收）

- 目標：用使用者的角度寫要解決什麼問題。
- 整體驗收：用外部看得到的行為寫，不寫實作細節；說明在哪個最高層的接縫驗證，接縫越少越好，理想只有一個。
- 不做什麼：明寫範圍外的事，避免旁支膨脹。
- 不寫檔案路徑與程式片段，它們很快過時；除非原型已證明某個決定，且文字說不清。

## 三、拆票（寫成 LOOP 的計畫表）

- 每張票是縱切：從資料到介面到測試的一條窄而完整的路，做完能單獨展示或驗證；不是只做一層。
- 每張票的大小要能在一個乾淨的上下文做完。
- 每張票寫清楚「被誰擋住」；沒有擋的可以立刻開工。重構要先做，讓後面的票變簡單。
- 例外：一個機械式改動影響全碼的寬重構，用「先加新的、分批搬、最後刪舊的」三段，不硬切成縱切。
- 拆完給使用者看編號清單（標題、被誰擋、做完能做到什麼），只問三件事：粒度對不對、擋住關係對不對、要不要合併或再切。使用者核准才定案。
- 專案有看板時，依專案規則一票一卡；沒有看板就只進 LOOP 計畫表，不另建。
