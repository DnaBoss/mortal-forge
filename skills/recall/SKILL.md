# 專案盤點與推送

把目前專案的工作保存到可核對的遠端版本。這是手動工作流程，不安裝自動推送 hook 或排程；技能被載入不代表獲得寫入授權。

## 範圍

- 「只盤點」只讀；「盤點並推版／提交推送」授權整理本次範圍、commit 與一般 push，不包含新合併、部署、發布 tag、刪分支或強推。沿用本輪及前文的授權，不重問已明確的事項。
- 裸呼叫此技能時，先盤點；沒有前文推送授權就完成盤點後詢問推送。若使用者已要求推送，依目前分支與既有 upstream 決定一般目標，不要求使用者重述可查明的資訊。
- 預設目前 repo／分支。其他 worktree、分支只盤點；只有明確納入範圍才推送。若目標是「全部異動」，先列出有哪些不同工作，不將他人的進行中修改當成本次成果。
- 推送若會觸發部署或發布，沿用既有明確授權；未授權時先完成本機準備，再說明具體觸發條件並詢問。未知的發布設定不能宣稱不會部署。
- 判定例：只盤點時 commit 與 push 都禁止；目前分支已授權且驗證通過時，另一工作樹有不相關修改不阻擋目前分支推送；提交前檢查失敗不得新增 commit。一般 push 授權不包含它觸發的部署，兩者分別核對。

## 固定收斂流程（使用者 2026-10-20 授權）

每次 recall 不只盤點，還要把可安全完成的本機工作收斂；除非使用者當次明確說「只盤點」。

1. 把未提交內容按工作目的分開審查與提交，不混合不同功能，不使用 `git add -A`。無法確認來源或仍在進行的他人修改不提交。
2. 對每個候選功能跑專案完整檢查。只有功能完整、完成判準全綠、沒有未決風險時才合進 repo 指定的整合分支；本專案的整合分支是 `dev`，不得臆造 `develop`／`devlop`。
3. 合併後推送整合分支並讀回 SHA。若推送會觸發未授權部署，先完成本機合併準備並停在推送前。
4. 確認整合分支已包含來源分支提交後，刪除該來源的本機與遠端分支。不得刪除尚未完整、未合併、被其他工作樹使用或不屬於本工作階段的分支。
5. 從最新整合分支建立 `feature/<next-slug>` 繼續下一項已知工作；沒有明確下一項時不建立空分支。
6. PDF 必須分開回報每個工作的 commit、完整檢查、merge、push、遠端讀回、分支刪除與新分支；任何一步未完成都要寫原因。

## 盤點

1. 讀適用的 AGENTS.md 與專案檢查設定。用 `git rev-parse --show-toplevel` 確認 repo；確認分支、remote、upstream、hooks、工作樹與正在執行的工作。remote URL 若含憑證，回報時遮蔽。
2. 查看 `git status --short --branch`、`git worktree list --porcelain`、已暫存及未暫存 diff、未追蹤檔、未推送提交。區分「未提交修改」與「已提交但未推送」；乾淨工作樹不等於已同步。
3. 只盤點模式可用 `git ls-remote` 讀遠端，不執行 fetch 或其他寫入。推送模式先 fetch 選定遠端，核對共同歷史與 ahead／behind；無 upstream 時依已查明的 remote 與同名分支設定，不猜測多個候選遠端。
4. 從程式入口、實際產物與可執行檢查描述現況。LOOP、README 與舊報告僅是線索；沒驗的行為寫「未查證」。不因盤點而重跑真實資料收集或模型任務。

## 保存與驗證

1. 審查要發布的完整差異與新提交，排除憑證、本機資料庫、個人資料及非本次產物；遵守專案對研究產物的規則。逐檔或逐區塊暫存，不盲目 `git add -A`。
2. 保留原有 staged／unstaged 邊界與他人修改；有混合內容無法安全分離時，先完成不依賴它的工作，再說明具體阻擋。不自動 stash、restore、reset、clean，也不切換活躍工作樹來掩蓋差異。
3. 已有提交就驗證後推送，不製造空提交。需新增提交時遵守分支政策與 Conventional Commits；受保護主線上的修改使用合規工作分支，不直接提交主線。
4. 依實際 manifest、CI 與專案 gate 跑格式、靜態檢查、測試；推送前完成要求的全套。缺工具先用既有安裝方式補齊；缺環境或失敗就記錄阻擋，不略過或放寬 gate。純文件無對應測試時明說不適用，不虛構通過。
5. 檢查的是實際 outgoing commit。測試後再核對 HEAD、index 與工作樹；有新變更須重新審查及驗證受影響部分。推送期間不改檔。保留 hooks；hook 必要重跑照常執行，其他已通過且無新變更的檢查不重跑。

## 推送與讀回

- 明確指定已確認的 remote 與 ref，一次處理一個已驗證的目標；不用 `--all`、`--mirror`、`--force` 或 `--no-verify`。遵守專案對目前 checkout 與推送 commit 一致的要求。
- 記下本次推送的完整 SHA。推送成功後以 `git ls-remote <remote> refs/heads/<branch>` 讀回，與該 SHA 比對，再查本機狀態。遠端已前進到別的 SHA 時，查明是否包含本次提交，不能直接宣稱版本一致。
- 連線逾時先查遠端：若已收到提交就不重送；若沒有且原因已排除，才做一次有界重試。非 fast-forward 或遠端分歧先查原因；不自行 rebase、合併或強推。
- 有 CI 就查本次 SHA 的執行結果；尚在跑或無法讀取照實標示。無 CI、push 成功、本機測試通過是不同事實。
- 不因收工提示而變更他人的 PR 狀態。需要操作 PR 時先核對作者、提交者、工作階段歸屬及授權。

## PDF 回報

1. 完成盤點或授權的提交推送後，讀取並執行 PDF 技能，交付繁中 PDF；只盤點模式也適用。使用者當次明確要求純文字時例外。不得以 HTML 代替，也不交付中間排版檔。
2. 使用 `scripts/render_recall_pdf.py` 產生 1–2 頁橫式儀表板。JSON 輸入與 PDF 放在 `~/.local/state/recall/reports/`，避免只盤點時污染專案工作樹。
3. 報告必須直接回答三題：「已做什麼」、「還沒做什麼」、「為什麼停下」。Git 數量只作證據，不得取代工作成果與停點說明。
4. 第一眼必須看懂結果：最上方放一句結論；用大數字顯示已完成工作、待完成工作、未推送提交與失敗檢查；用狀態表分開 commit、push、merge、CI、部署。
5. 只呈現本輪證據。從提交、實際產物、測試、PR／CI、LOOP checkpoint 與系統紀錄判斷。若無法證明因停機、技術困難或外部依賴而停止，就明寫「原因無紀錄」，不可猜測。
6. 分支、短 SHA、遠端讀回、已跑／未跑檢查、剩餘修改與阻擋用短句或表格；能用數字、時間線或狀態圖表達就不寫長段落。沒有基準或實測數字時不得畫趨勢或百分比。
7. PDF 必須標明盤點時間、範圍與資料邊界。未完成、執行中與未查證使用不同狀態，不得標成完成。長時工作未完成時呈現當前狀態，不等待它完成。
8. 產生後以 `pdfinfo`、`pdftotext`、`pdftoppm` 驗證頁數、可搜尋文字及視覺版面；實際查看每一頁，修正截斷、重疊與過小文字。
9. 最後只用一至兩句回覆重點與 PDF 連結，不在聊天重貼整份盤點。產生失敗時保留精簡文字結果，不宣稱已有 PDF。
